I'm **Suraj Dusane**, a full-stack product engineer. I like building products

ProWater is a solo project. I designed the 12-table schema, wrote the 24-month
simulation, built the tRPC API and the Next.js UI, tuned the charts, and wrote
this case study. The company is fictional; the schema, queries, and scoring
paths are real code running against a deterministic dataset.

I care about making complex systems legible. A risk score should show its
evidence. A ranked queue should explain its ranking. A docs page should let a
reviewer verify a claim in one click instead of trusting a screenshot.

## What I was optimising for

The temptation with a portfolio project is to add more pages. I optimised for a
coherent product story instead.

- **Two ideas, deeply implemented.** Predictive service demand and household
  churn risk both start with a decision, not a CRUD form. Each has a documented
  method, a real query path, and a screen built around acting on the result.
- **A schema that reflects the domain.** Areas, societies, households, plans,
  subscriptions, dispensers, readings, tickets, complaints, payments,
  technicians, and leads are separate tables because they behave differently.
  The model is not a generic “users and items” template.
- **A simulation that makes the insights real.** The seed generates 24 months of
  causal history — filter degradation, service tickets, complaints, payments,
  and churn — so the risk and demand signals are earned by the data rather than
  hard-coded.
- **Documentation a reviewer can verify.** Every performance and quality claim
  links to the file that implements it. Where something is missing, the page
  says so.

## How I work

- Start with the decision, then the data, then the UI.
- Build one vertical slice at a time: schema, query, router, hook, component.
- Prefer boring, explainable models over black boxes.
- Write the trade-off down while it is still fresh.
- Treat loading, empty, and error states as part of the feature, not cleanup.

## What I'd build next

1. **Real telemetry ingestion.** A write endpoint for dispenser readings with
   idempotency keys, late-arrival handling, and per-device retention. Today the
   series is generated by the seed.
2. **Auth and tenancy.** Organizations, membership, row-level scoping, and an
   audit log for mutations. The current `authorizedProcedure` is an alias, not a
   gate.
3. **A calibrated churn model.** Learn the weights from observed cancellations,
   backtest them, and monitor drift. Keep the rule-based score as the
   explanation layer rather than replacing it.
4. **Tests and observability.** Unit tests for scoring, integration tests
   against a disposable Postgres database, Playwright smoke tests, structured
   logs, and error tracking.
5. **Route optimisation for field service.** Use the society coordinates already
   in the schema and SLA windows to sequence technician visits. The board is
   manual today.

## A note on the demo

ProWater is public and has no authentication. Mutations are live and shared: if
you move a ticket or mark a payment paid, every visitor sees it. The data is
simulated. `bun run db:reset` restores the dataset, and `bun run db:seed` adds
another deterministic copy only when the database is empty.

The company is fictional. The code is not.
