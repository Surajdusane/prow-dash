ProWater is a full-stack ops dashboard for a piped RO water business: I modeled
the domain, simulated 24 months of causal data, and built two predictive
workflows — area-level service demand and household churn risk — behind a typed
tRPC API and a server-rendered Next.js UI. The company is fictional; the schema,
the queries, and the scoring paths are real code running against a deterministic
dataset.

## The two questions

**Where will service demand concentrate next, before complaints pile up?** The
Service Ops page ranks dispensers by TDS slope and filter age, so the team can
schedule a filter change in Whitefield before the household calls. The list is a
batch query over the last 30 days of readings, not a streaming model. Start at
[/service-ops](/service-ops); the
[full method](/docs/ideas/predictive-service-demand) explains the triggers.

**Which households are about to churn, and why?** The Customers page scores
every household from complaints, late or failed payments, SLA misses, and
tenure. A 0–100 score sorts the book, and the drawer shows the evidence behind
it. Start at [/customers](/customers); the [full method](/docs/ideas/churn-risk)
explains the weights.

## What I built

- A 12-table Postgres model covering areas, societies, households, plans,
  subscriptions, dispensers, readings, tickets, complaints, payments,
  technicians, and leads.
- A deterministic 24-month simulation: `faker.seed(42)`, ten seed stages, and
  causal patterns from filter degradation to churn.
- Nine dashboard routes across operations, growth, revenue, devices, and
  sustainability.
- A fully typed path — tRPC v11, TanStack Query v5, Drizzle ORM, Zod v4 — with
  no mock JSON in the client.
- Server-rendered pages with batched prefetch, Suspense boundaries, shaped
  skeletons, and error boundaries with retry.

## How I approached the work

1. Researched the service and the data it produces: societies, subscriptions,
   dispensers, telemetry, service tickets, complaints, payments, and leads.
2. Designed the schema around the decisions the dashboard must support, not
   around a generic entity list.
3. Chose Next.js full-stack so there is no separate backend to maintain or
   deploy.
4. Chose TypeScript, tRPC, TanStack Query, Drizzle, and Zod for one type-safe
   path from database to component.
5. Wrote a deterministic seed with injected patterns, so every chart has a cause
   rather than random noise.
6. Built one feature at a time: query → schema → router → prefetch → hook →
   component.
7. Chose the chart and route only after the data and the decision were clear.
